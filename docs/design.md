# 設計ノート — やねうら王フォークによるついたて将棋エンジン

2026-08-27 初版。

## 0. なぜフォークか

前作 tsuitate-bot (Rust) の調査メモ(`tsuitate-bot/docs/yaneuraou-lessons.md`)の結論:

> 「1局面に対する操作」はほぼ全部そのまま粒子に対して使えるが、
> 「木を掘る」系の技術は土台ごと無い。相手手が観測でしか分からないので木が張れない。2手読みが限界。

この「木が張れない」を突破するのが本作の主眼。**確定化サンプリング**では
粒子(=相手配置の具体的な仮説)ごとに完全情報の局面が確定するので、
その上では普通のαβ探索が任意の深さまで回せる。やねうら王から借りるのは:

- `Position` / `movegen` / 合法性判定(打ち歩詰め・自玉放置まで完全一致でサイトの反則判定と同じ)
- MaterialLv9評価関数(利き数・距離減衰・紐・玉周辺の穴。連載版の実測でR2700相当。外部ファイル不要)
- 利きの差分維持(`LONG_EFFECT_LIBRARY`)・1手詰め(`mate_1ply`)・弱3手詰め
- ビルド基盤(新エディション `TSUITATE_ENGINE` をMakefileに追加)

前作はGPL回避のため「アイデアだけ読んで自前実装」だったが、
本作はフォークなのでリポジトリ全体をGPLv3にして制約を外した。

## 1. 観測モデル(サイトの仕様の写し)

サーバー(tsuitate リポジトリ `judge.ts` / `events.ts`)の裁定:

- 反則 = **完全情報の通常将棋ルールで不正な手**(経路封鎖・打ちマス占有・二歩・
  打ち歩詰め・自玉放置すべて)。理由は通知されない。手番は変わらない。累計10回で反則負け
- 取った駒は盤上種別(成駒あり)で通知、取られたら**マスだけ**通知
- 王手宣言は正規手の直後に両者へ通知
- 合法手が無い(詰み・ステイルメイト)= 手番側の負け

エンジンの入力はこれで全部(`GameHistory` = `HistEvent` の列)。

### 王手宣言のタイミング

`game:check` は着手イベントの直後に同期的にemitされる。Socket.IOは同一接続でFIFOなので、
「次のイベントか`go`が来た時点で、直前の着手の王手宣言なし(=王手なし)が確定する」
というルールで遅延確定させる(`CheckAfter::Pending` → `Yes`/`No`)。
王手の**否定**も強い観測(粒子の玉位置を大きく絞る)なので、なし確定を必ず流すこと。

## 2. 信念状態(belief.h/cpp)

粒子 = ヒレの初期局面から観測と矛盾しない手順で到達できる完全局面1つ。
`Particle` は `Position` + StateInfoの列 + 自分が選んだ相手手列(`oppMoves`、リプレイ用)。
自分側の駒は全粒子で共通(完全既知、`OwnView`)。

### 更新則

| イベント | 粒子への操作 |
| --- | --- |
| 自分の正規手 | その手が合法・取った駒一致(盤上種別まで)・王手宣言一致の粒子だけ残して進める |
| 自分の反則手 | その手が**不正**な粒子だけ残す(合法だった粒子は矛盾) |
| 相手の着手 | 粒子上の合法手のうち観測(取られたマス・王手宣言)と整合する手を方策でサンプリングして進める。整合手ゼロなら死 |
| 相手の反則 | 制約なし(真の局面と無関係) |

相手手の方策 = 着手後の静的評価のsoftmax(温度120cp) + 10%一様。
これは「相手はこちらの駒が見える」前提の千里眼バイアスを持つ(既知の近似)。

### 再生成の3段構え

粒子は必ず枯れる(特に自分の反則と捕獲の成り状態不一致で大量死する)。再生成は:

1. **部分若返り** — 死んだ粒子の相手手列を種に、**直近R手だけ**(R=2→4→8→16)
   整合サンプリングし直す。全滅の原因は直近の手にしか依存しないことが多く、
   ゼロからの全リプレイ(成功率がplyに対して指数的に落ちる)よりはるかに成功しやすい。
   種は墓場(リングバッファ256)から**最長生存**のものを優先する
   (古い短い種は「それ以降全部一様サンプリング」になり必ず序盤で死ぬ。実測済みの罠)
2. **緩和リプレイ** — 制約を弱い順に外す。relax1: 自分の反則制約と「王手なし」制約、
   捕獲駒の成り状態(生駒種一致までに緩める)。relax2: さらに「王手あり」。
   捕獲のマス・自手の合法性は絶対に外さない(駒勘定が壊れるため)。
   緩和粒子はp_legal推定を汚すので**最低限の数の確保にしか使わない**
3. **合成粒子** — 履歴を捨て、現在の駒勘定と王手状態だけ満たす配置を直接サンプリング。
   駒勘定の保存則:
   - 相手側の駒総数(種別ごと) = 全体 − 自分の盤上 − 自分の持ち駒 (**厳密**)
   - 盤上/持ち駒の分割は観測不能(相手の打ちは見えない)。
     「取られた自駒の累計」を上限に、7割持ち駒と仮定してサンプリング
   - 王手を受けているときは王手駒を最後に明示配置する(偶然の王手を待つと失敗する)

  ※「自分の盤上駒数は初期配置が上限」という仮定は**誤り**(取った駒を打つと超える)。
  一敗地にまみれたので注意(駒勘定は必ず保存則で書く)。

時間配分: 同期(sync)は思考予算の40%を上限に、緩和ラダー80%+合成予約20%。

### 実測の効き(belief同士4局・500ms/手)

| 施策 | 0粒子思考 | 選択手の平均p_legal | 平均手数 |
| --- | --- | --- | --- |
| 素朴(全リプレイのみ) | 21% | 68% | 44 |
| +部分若返り | 15% | 75% | 66 |
| +種の質(最長優先) | 10% | 78% | 54 |
| +合成粒子+駒勘定修正 | **0%** | **89%** | **136** |

## 3. 手の選択(think.cpp)

```
combined(m) = p_legal(m) × E[squash(探索値) | mが合法な粒子] + (1 − p_legal(m)) × foulCp
```

- `p_legal` は全粒子での合法率。候補手 = 「自分の駒だけを考慮した」手
  (サイトのmove-hints.tsと同じ意味論)から、この手番で反則になった手を除いたもの
- stage1: 全候補×粒子24個の静止探索で粗く序列化 → 上位12手だけ
  stage2: 粒子48個×深さ2から反復深化(時間で打ち切り)
- 探索値は±2500cpで飽和、詰みは±3000(粒子平均が発散しないように)
- **反則コスト**: `-(100 + 60f) × 10/(10-f)`(f=反則累計)。
  さらに信念品質が悪いときに割増(緩和レベル×1.5倍、粒子数1/4未満で2倍)。
  固定コストだと終盤に反則予算を使い切って反則負けするスパイラルが実測で出る
- 0粒子時の保険は「見えない駒に当たりにくい手」(短い移動・打たない)優先。
  ただし現状の実装では合成粒子があるため実質的に到達しない

## 4. 審判つきアリーナ(arena.cpp)

完全情報のPositionを持つ審判がサイトのjudge.tsと同じ裁定でエンジン同士を対戦させる。
`belief`(本体)と `heuristic`(前進+成り+乱数 = サイト内蔵bot相当)が選べる。

```
printf "arena games 20 budget 300 particles 128 [p2 belief] [seed N] [verbose]\nquit\n" | ./YaneuraOu-by-gcc
```

診断行(`belief diag:`)に 0粒子思考数・緩和レベル・選択手のp_legal・
反則の帰属(0粒子時/緩和時)が出る。**変更はこの数字とセットで評価すること**(前作の規律を継承)。

## 5. 既知の限界と次の一手

1. **時間超過気味** — budget 500msに対し実測~850ms/手(再生成が食い込む)。
   本番のフィッシャー300+3では予算式を保守的にしてあるが、
   `sync`/`stage2`の締め切り厳守をもう一段固くする余地がある
2. **千里眼バイアス** — 相手手方策も確定化探索も「相手はこちらが見える」前提。
   相手の視界(こちらの駒が見えない)をモデル化した方策が次の大玉。
   前作の知見: 相手玉位置ビリーフの質が攻めの評価の律速
3. **重み無しの粒子** — 全粒子等重み+棄却。観測尤度による重み付け(SIR)にすると
   王手否定などの弱い証拠を捨てずに使える
4. **探索が自前の簡易negamax** — やねうら王本体の`YaneuraOuWorker`(LMR・TT・history付き)を
   粒子探索に使う配線は未着手。stage2の深さを上げるならこちらが本筋
5. **NNUE** — MaterialLv9で始めたが、NNUE評価(halfKP)に差し替え可能な構造。
   評価ファイルの配布と強さ/速度のトレードオフは未検証
6. **オフライン再現** — 前作のscenario(実戦の局面再現)に相当する仕組みは未移植。
   実対局の記録(ブリッジ側でJSONL化)から始めるのがよい
